PSG REBRAND CURRENT VS FUTURE PRODUCT, UX, UI AND FUNCTIONALITY AUDIT
=======================================================================

Status: Analysis and recommendations only.
No application code, database schema, migrations, packages, Supabase records, or production data were changed.

Purpose
-------
This audit compares the actual current implementation with the approved Business Rules and UX Specification and the Definitive Relational Database Specification.

The product direction is:

  A branch-first PSG rollout control centre where every branch has one rebrand workspace, a fixed lifecycle, configurable task checklists, clear current work, explicit status, shared task editing, reliable files, formal approvals, clear communication, and immutable history.

EXECUTIVE ASSESSMENT
--------------------
The current app is a useful operational prototype, but it is not yet the approved product architecture.

It currently feels like:

  A partially consolidated internal admin/project-management system with a useful branch view, rather than a finished national rollout control centre.

What is already valuable:

  - Supabase-backed authentication and data access
  - Responsive React structure
  - Branch list and branch detail flows
  - Project/task/file operations
  - Task-linked files
  - Task comments and updates
  - Basic role policies
  - Map and reporting foundations
  - Storage upload, preview, download, rename, and delete flows
  - Error boundaries and query caching

What is structurally wrong:

  - Branch and Project are still competing primary concepts.
  - Branch Details and Project Details duplicate operational information.
  - Tasks, files, comments, questions, and activity remain embedded in project JSONB.
  - The current code still requires task assignees even though the approved rules do not.
  - The current task is inferred rather than explicitly stored.
  - Current task statuses are Pending/Open/Busy/Done rather than the approved states.
  - There is no My Actions view.
  - There is no relational approval, request, notification, or audit model.
  - Role definitions, UI role options, type normalisation, and permission defaults disagree.
  - Current RLS policies are too broad for the target security model.
  - Live schema drift has already caused production project creation failures.
  - The dashboard is mostly metrics plus embedded reports, not an attention-based control centre.

The app should not be refactored page-by-page without first resolving these model conflicts.

1. CURRENT APPLICATION ARCHITECTURE
-----------------------------------

Framework:
  - React 19
  - TypeScript
  - Vite
  - React Router
  - Tailwind CSS
  - TanStack Query
  - React Hook Form
  - Zod
  - Supabase Auth, PostgreSQL, and Storage
  - Leaflet / React Leaflet

Application entry:
  - src/App.tsx

Shared shell:
  - src/layouts/AppShell.tsx

Current route architecture:
  - Lazy-loaded page modules with chunk-reload recovery
  - AuthProvider wraps the application
  - SaveFeedbackProvider provides global save notifications
  - AppShell wraps all authenticated routes
  - RouteErrorBoundary catches render failures
  - Supabase reachability is checked after authentication

Current state/data approach:
  - TanStack Query loads branches, projects, users, and individual projects.
  - Project data is mostly loaded as one large projects collection.
  - Many mutations read the existing project, mutate arrays in memory, and write the complete tasks/files/comments/activity JSONB fields back to projects.
  - LocalStorage is used as a fallback for branches, projects, profile identity, and notification retry data.
  - The frontend maps database rows into domain objects in portalService.ts and branchService.ts.

Main architectural weakness:
  The service layer is a compatibility layer around a denormalised JSONB project document, not a domain API for branch workspaces and relational operations.

Security weakness:
  The current SQL schema grants broad authenticated access and includes public read policies for branches/projects. Frontend checks are not a sufficient security boundary.

6. BRANCH WORKSPACE AUDIT
-------------------------
The current BranchDetailPage already contains useful pieces:

  - Branch identity
  - Location
  - Contacts
  - Project count
  - Outstanding task count
  - File count
  - Current task highlight
  - Quick updates
  - Pending tasks
  - All tasks
  - Task files
  - Task comments
  - Preview/download/rename/delete
  - Recent updates/activity

However, it is not yet the approved Branch Workspace because:

  - It can render multiple projects for a branch even though the target is one primary workspace.
  - It has no explicit current_task_id.
  - It infers the current task as the first unfinished task.
  - It still uses old task terminology and status values.
  - It has no stage timeline for the fixed 14-stage lifecycle.
  - It has no health model separate from project status.
  - It has no approval tab.
  - It has no required-file/missing-file summary.
  - It has no responsible role/responsible person display.
  - It has no My Actions context.
  - It duplicates ProjectDetailPage functionality.
  - Quick update and task operations are spread across long scrolling sections.

Recommended top-to-bottom hierarchy:

  1. Branch header and identity
  2. Health, stage, progress, and dates
  3. Current task card with status, responsible role, required action, and blocker
  4. Attention strip: approvals, blockers, missing files, overdue work
  5. Stage timeline
  6. Current task action panel
  7. Workflow task list
  8. Files and missing-file summary
  9. Communication and requests
  10. Approvals
  11. Activity history

Branch Details and Project Details should be merged into one route, with the current project route redirecting to the branch workspace.

7. WORKFLOW UX AUDIT
--------------------
Current implementation:

  - Project stages are free-form strings.
  - Timeline derives stages from task.stage or task.text.
  - Workflow status is inferred from completed tasks.
  - Project status is recalculated from stage/task state in some paths.
  - There is no fixed stage table.

This directly conflicts with the approved fixed lifecycle.

Recommendation:
  Use a hybrid vertical stage timeline plus task list.

Why vertical:
  - The 14 stages are too many for a reliable desktop-only horizontal timeline.
  - Mobile needs a readable sequence.
  - Long stage names need room.
  - A vertical timeline can show completed/current/future/blocked states clearly.

Each stage displays:

  - Stage number
  - Stage name
  - Stage status
  - Completion date
  - Required files summary
  - Approval state where relevant
  - Task count
  - Expand/collapse action

Stage states:

  - Complete: green and collapsed by default
  - Current: strong highlight and expanded
  - Future: neutral
  - Blocked: red warning and blocker reason
  - Waiting: amber warning
  - Skipped/cancelled: muted with explanation

The lifecycle should be stored in workflow_stages rows protected as system data.

8. TASK UX AUDIT
----------------
Current task implementation is incompatible with the approved task model.

Current code still contains:

  - TaskAssignee type
  - assigneeName
  - assigneeEmail
  - assignees array
  - buildTaskAssignees()
  - required assignee validation when adding tasks
  - “Assign every open task to at least one person” errors
  - task assignment UI
  - participant summaries derived from assignees
  - current task display showing assigned people
  - old task statuses pending/open/busy/done

This is a critical mismatch.

Current task creation can fail because no person is assigned. That must be removed in the future design.

Future task record should use:

  - stage
  - title
  - description
  - status
  - priority
  - sort order
  - due date
  - responsible group
  - optional responsible person
  - required action
  - waiting reason
  - blocker reason
  - required completion checks
  - created/updated/completed actor fields

Task interaction should allow a user to:

  - Change status directly
  - Select responsible role
  - Optionally select a responsible person
  - Add a required action
  - Add/update blocker reason
  - Add waiting reason
  - Set priority and due date
  - Upload required files
  - Add a quick update
  - Complete/reopen where permitted

The task card should not require users to navigate to another page for common actions.

9. CURRENT TASK AUDIT
---------------------
CurrentTaskCard.tsx uses:

  project.tasks.find(task => !task.completed)

This is not acceptable for the target model.

Problems:

  - It ignores explicit current task selection.
  - It may select a Pending/Waiting task that is not the true current task.
  - It displays assigned-user language that the approved model is removing.
  - It provides a quick update but no explicit task status or responsible role.

Future:

  - Add workspace.current_task_id.
  - Display current task prominently.
  - Show status, responsible group, optional person, due date, required action, blocker, and missing files.
  - When complete, suggest the next task but require intentional confirmation.

10. FILE UX AUDIT
-----------------
Current implementation:

  - Files are stored in Supabase Storage.
  - Metadata is stored in projects.files JSONB.
  - Files may have taskId.
  - Branch and Project Details support upload/preview/download/rename/delete.
  - Upload errors were recently made visible.
  - Upload now refreshes latest metadata before appending.

Problems:

  - File metadata and storage are duplicated without a relational file record.
  - No categories are required.
  - No versions are preserved.
  - No required-file checklist exists.
  - No approval-file relationship exists.
  - File deletion currently depends on project JSONB update plus Storage removal.
  - Storage policy and project-row policy must remain perfectly aligned.
  - Missing metadata and orphaned Storage objects are difficult to identify.
  - The accepted MIME list is not perfectly aligned between app validation and SQL bucket configuration.

Future file UX must show:

  - Required files
  - Present files
  - Missing files
  - Category
  - Version
  - Uploaded by
  - Date
  - Approval state
  - Task/workspace relationship
  - Preview/download/delete actions

12. COMMUNICATION AUDIT
-----------------------
Current implementation stores comments, questions, answers, request metadata, and activity inside projects.comments and projects.activity.

The Project Details UI does distinguish some task comments and questions, but the data model does not provide durable separation.

Future separation:

  Updates:
    Human progress information with no response requirement.

  Requests:
    Messages requiring a response, with response history and status.

  Approvals:
    Formal decision records.

  Activity:
    Automatic immutable system events.

Do not create one generic feed that attempts to represent all four concepts.

My Actions does not currently exist.

The current application has:

  - Dashboard task summary in a limited form
  - Task assignee logic
  - Current task card
  - No responsible groups
  - No approvals table
  - No request-response table

Future My Actions should aggregate:

15. ROLE/PERMISSION AUDIT
-------------------------
Current role types include:

  - colourpix_admin
  - psg_user
  - psg_head_office
  - psg_branch_manager
  - sign_company

Critical code issue:
  normalizeRole() maps psg_head_office, psg_branch_manager, and sign_company to psg_user. This means the type-level role definitions and role policy definitions do not reliably survive authentication normalisation.

Access Controls issue:
  roleOptions currently exposes only colourpix_admin and psg_user, despite the type system and schema supporting more roles.

Current policy mismatch:

  - PSG Head Office policy is read/report/comment-oriented.
  - PSG Branch Manager policy is almost entirely read-only.
  - Sign Company policy is almost entirely read-only.
  - The approved future requires explicit installation and branch workflows.

Current task mutation mismatch:
  Task creation and editing require assignee data, which conflicts with the approved model.

Current frontend/RLS mismatch:
  UI checks are more restrictive in some places, but database policies in schema/repair SQL are broad authenticated/public policies. Frontend-only permission checks must not be treated as security.

Future authorization needs:

  - Global roles
  - Branch-scoped roles
  - Workspace-scoped access grants
  - Installer section restrictions
  - Role-based responsible-group actions
  - Permission-level decisions enforced in RLS/service layer

17. SUPABASE/RLS SECURITY AUDIT
------------------------------
Current schema risks:

  - Branches have public read policy in the schema.
  - Projects have public read policy in the schema.
  - Authenticated insert/update/delete policies use broad true conditions in the base schema/repair scripts.
  - Projects are not scoped by profile branch/workspace access at the database policy level.
  - Files need policy checks tied to workspace visibility, not only path shape.
  - Profiles require strict separation between self-editable identity fields and administrator-only role/access fields.
  - Activity needs insert-only/immutable semantics.

Target security model:

  - No public project/branch reads unless deliberately required.
  - Workspace visibility function/policy is the central RLS condition.
  - Installer access through explicit workspace_access_grants.
  - Commercial/approval files restricted by category or section permission.
  - Users cannot self-elevate.
  - Users cannot modify activity history.
  - Deletion and approval decisions require separate permissions.
  - Storage object policies must verify the associated project/workspace.

18. RESPONSIVE DESIGN AUDIT
---------------------------
Current strengths:

  - Tailwind responsive classes are widely used.
  - AppShell has a mobile header and fixed bottom navigation.
  - Project and branch cards collapse into responsive grids.
  - Task controls wrap on small screens.

Current problems:

  - mobileNavigation simply takes the first five primary navigation items rather than a role-specific mobile model.
  - Long branch/project workspaces create excessive vertical scrolling.
  - Accordion task bodies contain files, comments, inputs, and actions all at once.
  - Dense task controls can become difficult to use on phones.
  - No installation-specific camera/evidence workflow exists.
  - Tables/reporting need intentional mobile representations rather than simple wrapping.
  - Current content shell mixes light content background with dark nested panels, which can reduce hierarchy on small screens.

Future mobile priorities:

  - Current task card first
  - One-tap status change
  - One-tap blocker action
  - Camera upload for evidence
  - Compact file list
  - Full-screen task detail drawer/page
  - Sticky save/action control
  - Role-specific bottom navigation

19. VISUAL DESIGN AUDIT
-----------------------
Current visual character:

  - Dark navy outer shell
  - Light grey content panel
  - Dark translucent cards
  - Cyan, teal, green, amber, red, and purple accents
  - Large rounded corners
  - Many cards and nested cards
  - Strong Tailwind utility styling

Assessment:
  The UI currently feels like an unfinished internal admin system with a developing operational visual language, not yet a cohesive professional control centre.

Why:

  - Similar content is rendered in different visual systems across pages.
  - Branch and project cards use different hierarchy.
  - Status labels vary by page.
  - Dark cards inside a light shell can make the page feel visually fragmented.
  - Dashboard KPIs, report cards, task accordions, and project cards all use competing container styles.
  - Large rounded surfaces reduce information density for an operations application.
  - Some text is low contrast or inconsistent between dark and light surfaces.
  - Error and success messaging is not consistently local to the action that failed.
  - The visual language uses decorative surfaces where dense tables and clear lists would be more useful.

Recommended direction:
  Professional operational workspace, with dark navigation, light neutral content, restrained surfaces, strong status colours, dense tables, clear task hierarchy, and fewer nested cards.

20. PRIORITISED UX/FUNCTIONALITY PROBLEMS
-----------------------------------------
CRITICAL

C1. Task assignee requirement contradicts approved business rules.
Current: addProjectTask/updateProjectTask can reject tasks without an assignee.
Impact: Tasks cannot be created under the approved shared-task model.
Recommendation: Replace with responsible_group_id and optional responsible_person_id.

C2. Current task is inferred.
Current: first incomplete task is displayed as current.
Impact: Users may work on the wrong task.
Recommendation: Add explicit workspace current_task_id and intentional transitions.

C3. Old task statuses remain.
Current: pending/open/busy/done.
Impact: Waiting, blocked, not started, and in-progress semantics are unclear.
Recommendation: Migrate to approved statuses with required reasons.

C4. No relational operational model.
Current: tasks/files/comments/activity are JSONB arrays.
Impact: Weak search, reporting, concurrency, audit, and integrity.
Recommendation: Relational migration.

C5. RLS is too broad.
Current: base policies allow broad authenticated/public access.
Impact: Potential data exposure and unauthorised mutation.
Recommendation: Workspace/branch-scoped RLS before production redesign.

C6. Role normalisation collapses roles.
Current: non-admin roles may become psg_user.
Impact: Wrong permissions and wrong user experience.
Recommendation: Preserve exact role identity through auth/profile mapping.

C7. No explicit one-primary-workspace database constraint.
Current: duplicate prevention depends on IDs and frontend logic.
Impact: Branches can appear to have missing or duplicate projects.
Recommendation: Partial unique primary-workspace constraint.

HIGH

H1. Branch and Project pages duplicate functionality.
H2. No My Actions view.
H3. No dedicated Approval model or queue.
H4. No persistent notifications.
H5. No file categories, versions, or missing-file requirements.
H6. Dashboard lacks action queues.
H7. Search does not cover tasks/files/updates/activity.
H8. Project stage is free text and task-derived.
H9. Project health is conflated with project status.
H10. Installer access cannot be safely limited to installation sections.
H11. Users/access controls are not aligned with the approved role model.
H12. Live schema drift has already caused failed project inserts.

MEDIUM

M1. Reports are embedded in Dashboard instead of having their own route.
M2. Support is mailto-only.
M3. Profile image fields use URLs instead of uploads.
M4. Map coordinates rely on hard-coded fallbacks.
M5. Mobile navigation is not role-specific.
M6. Task accordions are too dense for mobile.
M7. Loading, empty, and error states vary between pages.
M8. Existing documentation describes functionality that is not implemented.

LOW

L1. About/Legal placement.
L2. Visual spacing and card-radius consistency.
L3. Icon/button standardisation.
L4. More polished report exports.

28. WHAT IS WRONG WITH THE CURRENT APP?
---------------------------------------
The main problem is not that the app lacks pages. It is that the current data model and user model do not match the approved business model.

The app has accumulated features around a project JSON document. This makes the interface look functional, but it creates contradictions:

  - Branch is supposed to be primary, but Project remains a competing object.
  - Tasks are supposed to be shared work, but code requires assignees.
  - Workflow is supposed to be fixed, but stages are free-form and task-derived.
  - Current work is supposed to be explicit, but current task is inferred.
  - Activity is supposed to be immutable, but activity is an editable JSONB array.
  - Files are supposed to be reliable, but file metadata is duplicated in JSONB.
  - Roles are supposed to be explicit, but role normalisation collapses role distinctions.
  - RLS is supposed to protect data, but base policies are broad.
  - Dashboard is supposed to guide action, but it primarily displays counts.

32. FINAL AUDIT CONCLUSION
--------------------------
The current application is a functional prototype with valuable operational building blocks, but it is not yet architecturally aligned with the approved PSG Rebrand Control Centre.

The most important work is not visual polish. It is resolving the domain model:

  - Branch as primary object
  - One active primary workspace per branch
  - Fixed stages
  - Relational tasks
  - Responsible group plus optional responsible person
  - Explicit current task
  - Separate task status and workspace health
  - Relational files and requirements
  - Formal approvals
  - Immutable activity
  - Scoped RLS and partner access
  - My Actions

The existing React/TypeScript/Vite/Supabase stack can support the future product. The current page structure, types, services, JSONB data model, permissions, and RLS policies cannot be carried forward unchanged.

The correct next step is to approve the unresolved business decisions, then implement Phase 1 in a separate migration-safe environment. No production refactor should begin before the current JSONB data has been mapped, backed up, and validated against the relational model.
