IMPORTANT HANDLING RULE
------------------------
This is an existing production-oriented application. Do not rebuild the Project Detail page from scratch. The current implementation already contains most required functionality. Revisions should simplify the existing page, improve hierarchy, and preserve data and workflows.

The branch rebrand workspace serves one PSG branch. Francois and Beverley manage the rebrand. PSG users primarily need to understand the current state, expected dates, next action, and latest update.

Do not add more widgets to solve hierarchy problems. Simplify, group, and reduce duplication.

============================================================
4. IMPLEMENTED RULES AND GUARDS
============================================================

A. Unified details editing
--------------------------
Implemented in `src/pages/ProjectDetailPage.tsx`.

The top branch/project details area has one read-only presentation and one edit mode. The same edit mode covers:

- Branch name
- Division
- Province
- Town
- Branch address
- Contact persons
- Current project stage
- Project status
- Target date
- Brief requested date
- Installation date
- Completion date

The read-only view is displayed by default. The user must click `Edit details` to see inputs. Save returns the section to read-only mode. Cancel closes edit mode without saving.

The save path is unified in `detailsMutation`. It updates branch data through `updateBranch` and project summary data through `updateProjectSummary`, then refreshes the relevant query state.

B. Editor identity restriction
------------------------------
The current UI displays the Edit details control only when the signed-in profile name, lowercased and trimmed, is `beverley` or `francois`.

This is an intentional current guard requested by the product owner, but it is not sufficient as a long-term security boundary. It must eventually be replaced with durable role/capability authorization enforced by backend/RLS rules.

Do not weaken Supabase RLS or treat this frontend check as security.

C. Delete protection
--------------------
The Delete project control is only visible while Edit details mode is open. It is not visible in read-only mode.

Deletion requires a second confirmation action. Closing edit mode clears the armed confirmation state. The delete mutation navigates away after success and uses the global save feedback surface.

D. PSG-facing simplification
----------------------------
The detailed internal Stages section is hidden unless the user is an internal management user. Current internal visibility is based on the existing internal-user calculation and role policies.

PSG-facing users should see project information, workflow/stage communication, latest updates, and permitted files, but not:

- Edit buttons
- Delete controls
- Stage administration
- Reorder controls
- Internal task management
- Internal history/administration
- Internal assignment details

The current Project Detail source hides the detailed Stages section for non-internal users. The top workspace still communicates the workflow through the read-only checklist.

E. Top checklist versus detailed Stages section
-----------------------------------------------
The top checklist is intended to be informational for communicating workflow progress.

The detailed Stages section is the internal management surface. It contains:

- Add suggested stage
- Add custom stage
- Expand/collapse controls
- Stage editing
- Stage deletion
- Detailed task status changes
- Reordering
- Task comments
- Task files
- Installation instructions

The top checklist must not duplicate internal management controls. If a future revision adds controls to the top checklist, the detailed section must be reviewed at the same time to avoid two competing edit surfaces.

F. Stage status labels
----------------------
The user-facing stage/task statuses are:

- Pending
- Started
- Busy
- Completed

The current relational mapping is:

- Pending -> `not_started`
- Started -> `waiting`
- Busy -> `in_progress`
- Completed -> `complete`

The Started -> `waiting` mapping is a compatibility decision, not ideal domain semantics. If the database supports a true `started` state later, migrate carefully and preserve existing records.

H. Communication hierarchy
--------------------------
The top workspace keeps Latest update as the compact status snapshot.

Internal users may see Project history. Detailed updates, questions, comments, and task communication remain available below for the workflows that require them.

A future simplification may consolidate these into an Updates area with a View all updates interaction. Do not delete the underlying comments/questions/activity data while changing the presentation.

I. Files
--------
File functionality remains available:

- Upload
- Preview
- Download
- Rename
- Delete
- Task association
- Thumbnail/preview loading

Files are intended to remain private and use signed URLs. A future UX revision may group client-facing files into categories such as Artwork, Quotes, Approvals, Site Photos, Installation Photos, and Final Documentation without removing task relationships internally.

J. No numeric percentage progress
---------------------------------
The previous numeric project percentage feature was removed from the active UI. The legacy database field may remain for compatibility, but it must not be displayed, edited, exported, or used as the primary user-facing progress mechanism.

Use workflow stages and statuses instead.

K. No project Notes feature
---------------------------
The previous project Notes editor/display was removed from the active UI. Do not reintroduce a separate Notes area. Use Updates, Questions, Comments, Project History, or task-specific instructions according to the communication purpose.

L. Save confirmation
--------------------
`src/contexts/SaveFeedbackContext.tsx` provides a global success/error toast.

The toast is used by the main save paths, including:

- Project details
- Branch/contact details
- Stage creation
- Stage editing
- Stage ordering
- Comments/updates
- File actions
- Profile saves
- User invites
- Access-control saves
- Project deletion

Project Detail success feedback is shown immediately after the mutation returns successfully, before cache invalidation completes, so a slow refresh does not make a successful action appear inert.

M. Contrast guard
------------------
`src/styles.css` contains a final dark-workspace contrast guard. It exists because older light-panel utility overrides conflicted with the navy workspace theme and produced black text on dark navy surfaces.

Current design rules:

- Normal text should meet WCAG 2.2 AA 4.5:1 contrast.
- Large text should meet 3:1.
- Meaningful UI boundaries and control indicators should meet 3:1.
- Dark panels use light slate/cyan/white text.
- Destructive red controls retain readable light text.
- Bright action buttons may use dark text where that gives stronger contrast.

Any future CSS work must preserve these constraints and should be checked in a browser, not only by reading Tailwind class names.
